# Zotrod · 个人主页

一个零依赖、零构建的静态个人主页。纯 HTML / CSS / JavaScript，直接托管在 GitHub Pages 上，手机、平板、电脑都能访问。

**设计目标：极简、克制、动效顺滑，且以后改起来不费劲。**

---

## 〇、页面结构：一共 6 屏

从上往下翻，每屏正好一屏：

| 屏 | id | 内容 | 数据在 config.js 的哪 |
| --- | --- | --- | --- |
| Q1 我 | `#top` | 头像居中、名字居中；下方两行两列：左微信 / 右 QQ（点复制）、左网易云 / 右小黑盒 | `site` / `profile` |
| Q2 在听 | `#listen` | 整屏专辑封面墙 + 歌曲磁贴（可站内试听），**由仓库定时任务自动同步** | `listen` |
| Q3 游戏 | `#gaming` | 游戏卡片：只有图标 + 名称 + 可复制 ID，不写介绍；竖版封面墙背景 | `gaming` |
| Q4 其他 | `#links` | 其余社交平台的链接卡片 | `links` |
| Q5 邮箱 | `#contact` | 邮箱，一键复制 / 直接发信 | `contact` + `site.email` |

现在是 **5 屏**。维修屏（`sections.repair.enabled = false`，2026-11-11 下掉）的
代码和数据都还在，想恢复只要把开关改回 `true`；导航编号会由渲染层自动重排，
不用手改 eyebrow 以外的任何东西。

想关掉某一屏：`config.js` → `sections` 里把 `enabled` 设成 `false`，导航会自动少一项。
Q1 是首屏（hero），不占 `sections`，永远第一屏。

顺序由 `sections.<key>.order` 决定（小在前），导航编号也照它排。
**这两个字段别省**：

- 少了 `order`，排序时会按 `0` 算，那一屏会静默跳到最前面，导航编号跟着错位；
- 少了 `label`，导航里直接印英文 key（会看到「02 listen」这种字）。

`sections.<key>` 里只放这三个字段（`enabled` / `order` / `label`）。
标题、正文、卡片列表属于**内容**，放在顶层同名键下（如 `gaming.items`）——
两处混写会让其中一处被覆盖。

## 三、风格与主题系统

风格（skin）和明暗（light / dark）是两个**互相独立**的维度，任意组合：**7 套风格 × 2 种明暗 = 14 种**。

| id | 名称 | 气质 | 圆角 | 标题字体 |
| --- | --- | --- | --- | --- |
| `ink` | 墨 | 黑白灰配墨绿，中性克制（默认） | 中 | 无衬线 |
| `paper` | 纸本 | 暖米纸色、棕褐点缀，印刷感 | 直角 | **宋体 / 衬线** |
| `noir` | 夜幕 | 高对比黑白配暗红，杂志感 | 小 | 无衬线（收紧字距） |
| `aurora` | 极光 | 青紫渐变光晕，未来感 | 大 | 无衬线 |
| `terminal` | 终端 | 磷光绿字，**全站等宽** | 直角 | 等宽 |
| `clay` | 陶土 | 暖灰 + 赭红 + 软阴影，有人情味 | 很大 | 无衬线 |
| `mint` | 薄荷 | 清透冷白 + 薄荷绿，轻盈 | 大 | 无衬线 |

### 三种切换方式

1. **主页右上角调色板按钮** —— 弹出面板，列出全部风格 + 明暗三段开关（浅色 / 深色 / 跟随系统）。访客的选择会记在自己浏览器里。
2. **`themes.html`** —— 14 种组合并排真实渲染（不是截图，是同一套变量注入到每张卡片里），点任意一格设为默认。
3. **`admin.html` → 外观** —— 改 `ui.skin` 这个**默认值**，决定访客首次打开看到哪套。

> 访客永远可以自己切，`ui.skin` 只是初始值。

### 加一套新风格

在 `assets/js/themes.js` 的 `list` 里复制一段改掉即可，**不需要动任何 CSS 或 HTML**：

```js
{
  id: "sepia",                  // 小写、可含连字符，不能重复
  name: "旧照",
  desc: "一句话说清它的气质。",
  swatch: ["#f2e8d5", "#2b2118", "#8a6b3f"],   // 面板上显示的三个色块
  base: {                       // 与明暗无关：字体、圆角、字距
    "font-sans": "...", "font-display": "...", "font-mono": "...",
    "r-sm": "4px", "r-md": "8px", "r-lg": "12px",
    "tracking-title": "-.02em", "border-w": "1px"
  },
  light: { /* 26 个颜色变量 */ },
  dark:  { /* 同样 26 个，一个都不能少 */ }
}
```

保存后刷新，主页面板、`themes.html`、编辑器外观页**三处都会自动出现**它。

### 变量清单（每套主题必须写全）

| 类别 | 变量 |
| --- | --- |
| 背景三层 | `bg` `bg-elev` `bg-soft` |
| 文字三层 | `text` `text-2` `text-3` |
| 线条 | `line` `line-strong` |
| 主色 | `accent` `accent-fg` `accent-soft` |
| 光晕 | `glow-a` `glow-b` |
| 阴影 | `shadow-sm` `shadow-md` |
| 头部 / 提示 | `header-bg` `toast-bg` `toast-fg` |
| 颗粒 | `grain-opacity` |

### 为什么"看着差不多"不够：自检会算对比度

```bash
node tools/verify-theme.js
```

696 项检查，其中最关键的是用 WCAG 公式算**真实对比度**，硬性阈值：

| 组合 | 下限 | 含义 |
| --- | --- | --- |
| `text` / `bg` | 12 | 正文必须清楚 |
| `text-2` / `bg` | 5.5 | 次级文字 |
| `text-3` / `bg` | 3.5 | 辅助小字（页脚、元信息） |
| `accent` / `bg` | 4.0 | 主色小标签要能读 |
| `accent-fg` / `accent` | 4.5 | 按钮文字压在主色上 |

还会检查：每套主题的变量键集合必须完全一致（漏一个就会串到别的主题的颜色）、圆角层级递增、阴影格式合法、`tokens.css` 的兜底值与默认主题逐项相同（否则 JS 没加载时会跳色）、风格页真的生成了 14 张带内联变量的卡片。

> 写这套检查时确实抓出 4 处不达标：极光/薄荷的辅助灰太浅（2.76、2.86），薄荷主色上的白字只有 3.44。都已按计算结果替换为达标色值。

### 接口

`window.SITE_THEMES` 上可直接调用：

```js
SITE_THEMES.list                 // 全部主题原始定义
SITE_THEMES.get('paper')         // 按 id 取一套
SITE_THEMES.ids()                // ['ink','paper',...]
SITE_THEMES.count()              // 14（风格 × 明暗）
SITE_THEMES.baseVars('paper')    // 只取形态层（字体/圆角）
SITE_THEMES.resolve('paper','dark')  // 合并后的完整变量表（键名不带 --）
```

`skin.js` 和 `gallery.js` 都调 `resolve()`，所以「实际生效的主题」和「预览页看到的」不可能分叉。

## 三之二、翻页式浏览（Apple 式章节）

页面默认是**翻页式**：一屏一章，上下翻动时吸附到页边界，右侧有页码。适合在社交场合拿给别人看——一页讲一件事，划一下就过去。

```
首页  →  关于  →  喜好  →  游戏  →  业务  →  联系
```

### 四种翻页方式

| 方式 | 操作 | 语义 |
| --- | --- | --- |
| **触摸滑动** | 上/下滑 | **不管距离，一次手势 = 一页**（像刷短视频） |
| 鼠标滚轮 | 滚一格 | 攒够 40px 判一次（鼠标一格约 100，触控板会碎成小块） |
| 键盘 | `↑` `↓` / `PgUp` `PgDn` / `j` `k` / `Home` `End` / `1–6` | 直接跳 |
| 右侧页码 | 点圆点 | 直接跳 |

### 触摸为什么「不管距离」

这条例外于滚轮，是刻意的：手指滑 20px 和滑 400px 都只翻一页。
位移**只用来判方向**，不参与阈值 —— 刷短视频的手感就是这样。

但下面四种情况必须排除，否则会误伤：

| 情况 | 处理 | 为什么 |
| --- | --- | --- |
| 位移 < 8px | 不翻页 | 否则点「复制微信号」会连带翻走一页 |
| 横向为主（\|dx\| > \|dy\|） | 让位给浏览器 | 留给以后可能出现的横滑组件 |
| 多指 | 不接管 | 双指缩放 / 三指不是翻页 |
| 有高个页（`snap=proximity`） | 让位给原生滚动 | 那页本来就该让用户自由滚 |

### 连翻锁：300ms，绝不为 0

翻一页后 300ms 内的滑动一律忽略。这个下限**不是为了手感，是为了正确性**：

`smooth` 滚动有 400~500ms 动画期，期间 `scrollTop` 一直在变，而 `activeIndex` 要等滚动停稳才更新。如果没有锁：

```
第一下 goTo(1) → 动画还在跑
第二下读到的 activeIndex 仍是 0 → 又 goTo(1)   ← 看起来「滑了没反应」
```

更糟的是 `activeIndex` 若已更新到 1，第二下就跳到 2 —— **第 1 页被整个跳过**。

为什么是 300 而不是滚轮的 460：手指抬起后人立刻准备下一次滑动，比鼠标滚轮节奏快得多。300ms 是「跟手」和「不跳页」的平衡点。`prefers-reduced-motion` 下滚动是瞬时的，锁收到 160ms。

> 这套行为有专门的回归测试：`node tools/verify-swipe.js`（12 项，用 CDP 真实触摸序列，不是合成事件）。
> 想退回「自由滚动 + 停手自动对齐」的老行为：`config.js` 里 `ui.swipePaging` 设成 `false`。

### 章节衔接：不是整块出现，而是逐层落位

翻到新一章时，页内元素会**逐项错开淡入并轻微上移**（`header` 先、卡片后，卡片之间再错开 60ms），同时顶部扫过一道极淡的光。这是「衔接自然」的来源——不是硬切。

三条实现上的约束：

1. **动画必须在目标页还在屏幕外时就开始**（`goTo` 里、`scrollTo` 之前挂 `is-entering`）。
2. **只给当前页播**，播之前先把其他页的标记清干净。早期版本没做这一步，从第 1 章跳到第 6 章时会途经中间几页，每一页都被挂上动画，多页同时开动、互相打架。
3. **每页只播一次**（`data-entered`）。手动滚轮 / 滑动进来的页不补播。

> ⚠️ 第 1 条是 2026-11-10 才改对的，原来写的是「只在滚动停稳 140ms 后播放」——
> 而平滑滚动本身要 700ms 左右，等它停稳时目标页的内容早就随着滚动露出来了。
> `@keyframes chapter-item` 的 `from { opacity: 0 }` 又把它们按回去重播：
> 屏幕上就是「内容亮了 → 整页变黑 → 再淡入」，实测在 866ms 处必然发生，
> 卡片上还叠着两层 `chapter-item`（轨道 + 卡片），暗得更明显。
> 当年为了防「途经的页乱播」而加的停稳判定，把动画推到了内容已经可见之后，
> 反而制造了一个每翻一页都出现、却从没被断言覆盖的闪烁。
>
> 现在的写法：动画赶在 `scrollTo` 之前开跑，那一刻目标页还在屏幕外，
> 藏起来没人看得见，滑进来的过程正好淡入，全程单调 `0 → 1`。
> 手动滚进来的页不补播 —— 用户是自己把内容拖进来的，再给它来一次淡入
> 只能制造同样的回跳。

> 另外三条也是实测踩出来的：第 2、3 条之间藏过一个更隐蔽的 bug ——
> 一度把「已播放」标记设在视口守卫**之前**，结果一旦被守卫跳过，这一页就永远
> 不会再播动画，表现是「有时有动画、有时没有」，跑三轮测试才稳定复现。

### 首次翻页提示

陌生人打开不知道这是翻页式的，所以首次进入会浮出一个小小的「上下滑动翻页 ↓」，**滚一下就消失**，同一会话只出现一次，8 秒无操作也自动收掉。

### 关键设计：吸附力度会自动切换

这是这套翻页能用的核心。做法是：JS 量出每一章的**真实内容高度**，只要有一章超过一屏，就自动降级。

| 情况 | 吸附模式 | 原因 |
| --- | --- | --- |
| 所有章都装得进一屏 | `mandatory` 强制吸附 | 任何滚动都停在页边界，翻页感最干脆 |
| 有任意一章装不下 | `proximity` 邻近吸附 | 否则用户读不到那章中间的内容 |

> 为什么不用一刀切的 `mandatory`：字体放大、系统字号偏大、小屏横屏，都可能让某章超出。那时强制吸附会把页面死锁在页边界上，用户**永远看不到被截断的部分**——这是可访问性事故，不是风格问题。

### 手机上的针对性处理

**1. 没有任何横向滑块。** 早期版本把卡片改成横滑（一屏一张半），后来全部去掉了：
横滑和上下翻页是两套方向的手势，在同一个页面上极易互相误触；
而且横滑区右边缘常常看起来就是最后一列，用户不知道还能划。
现在所有网格都是 `grid`，靠 `fit.css` 的按屏分档保证一屏装下（只压留白，字号有下限）。

**2. 页码改成底部细分段。** 浮在右侧的圆点会压在卡片上（实测重叠 14px）。改成贴着屏幕底边的 3px 分段：落在页面留白里，既能看出「第几屏 / 共几屏」，又完全挡不到内容。

**3. 触控反馈分两层。** 按下瞬间是 CSS 的 `:active` 微缩（约 3%，即时）；抬起时如果位移 < 8px 才补一圈涟漪。**滑动时不画涟漪** —— 加了「一次滑动 = 一页」之后，原先「按下就炸一圈」的行为会变成一屏屏划过去一路炸光，看起来像手游特效而不是主页。

### 关掉翻页

编辑器 → 外观 → 翻页与光效 → 取消「翻页式」，或改 `config.js` 的 `ui.paged: false`。会回到普通长页面，页码自动隐藏。

### 实现上的三个坑（都已处理）

1. **`body { overflow-x: hidden }` 会让吸附完全失效。** 它把 body 变成了滚动容器，html 上的吸附点就全废了——实测滚 400px 一格都不吸。改用 `overflow-x: clip`（能裁切但不创建滚动容器）。
2. **`position: sticky` 的页头会占掉文档流顶部 72px**，第一章永远差 72px 露不全，吸附落点会比预期多一个页头高度。翻页模式下改成 `fixed`。
3. **强制吸附会把页脚锁死**。最后再往下滚会被弹回最后一章，页脚永远看不到。给页脚加 `scroll-snap-align: end`，并让最后一章再按 `↓` 时滚到页脚。

## 三之二·四、Q1 的结构：一张名片，两个层级

```
              [ 头像 ]                     ← 居中
              [ 名字 ]                     ← 居中
            [ 一句话 / 身份 ]

   ┌──────────────┐  ┌──────────────┐      ← 主角：88px 实心白卡 + 微投影
   │ ▣ 微信  点击复制⧉│  │ ▣ QQ   点击复制⧉│         平台名 17px / 600 字重
   └──────────────┘  └──────────────┘         点整块就复制账号
    网易云音乐 ↗      小黑盒 ↗              ← 次要：40px 细线，浅灰底、无投影
```

**这一屏真正的主角是「怎么联系我」。** 微信号和 QQ 号是要交给对方的；
网易云和小黑盒只是"顺路看看"。它们的权重必须拉开，不能平起平坐。

为什么是**两列**而不是一列通栏：

- 原来的「微信 zotrod」是一条 760px 宽的横条，在宽屏上拉得很散，其实什么也没说；
- 两列让阅读路径变成「中间看人 → 左右扫联系方式」，和递名片的顺序一致；
- 手机上两列天然成立（每列约 140~170px），不需要额外断点。

### 账号为什么不印在卡上

早先卡里是「小标签 + 大账号」。两个问题：

1. **摆不下。** QQ 号 10 位、微信号 12 位，手机两列下每列只有约 170px，
   扣掉图标和内边距只剩 100px —— 必吃省略号；改成独占一整行，卡就变成两行高，
   和下面 40px 的外链条彻底失衡。
2. **看见了也得手抄。** 这张卡唯一的用途是把号码交给对方，
   而"点一下进剪贴板"比"看见再抄一遍"少一步，也不会被旁人顺眼记走。

所以现在卡面只有平台名，右边一行小字「点击复制」。账号仍在 `data-copy` 与
`aria-label` 里 —— 复制拿得到、读屏念得出，只是不再上屏。

### 主次靠四件事一起表达，不是只调字号

| | 联系卡（微信 / QQ） | 外链卡（网易云 / 小黑盒） |
|---|---|---|
| 高度 | 88px | 40px |
| 图标 | 40px，装在一块浅色方底里 | 18~20px 裸图标 |
| 底色 | 实心白卡 + 微投影（浮起） | 浅灰底、无投影（下沉） |
| 字重 | 平台名 600 / 1.06rem | 平台名 500 / .8rem 常规 |

只改其中一条都不够：单靠字号，外链卡仍会因为"多一行"而抢眼；
单靠颜色，缩小后又会变成两行看不清的小字。

**深色下要反向处理。** 深色主题的"抬升"是变亮（`--bg-soft` 比 `--bg-elev` 亮），
照搬浅色的灰底会让外链卡看起来比联系卡更高一档，主次正好颠倒 ——
所以深色里次要卡直接用页面底色 `--bg`，贴着背景才是"下沉"。

**配了封面的卡片是例外。** 若在后台给某张外链卡填了 `cover`，它本身就是一张缩略图，
压成 40px 细条会把图裁掉大半；这时改走「左边 40px 方图 + 右边单行」，高度不变。

手机上「平台名 + 点击复制」改成上下两行（图标跨两行居中），卡高约 67px，
仍明显高于下面 40px 的外链条，层级不变。

### 复制反馈不许动 DOM 结构

点联系卡复制时，图标曾被「已复制」三个字顶掉，整张卡塌一下再弹回来。
根因是反馈代码用 `btn.querySelector("span")` 找"要改文案的那个元素" ——
它命中的是**第一个** span，而联系卡的第一个 span 是图标容器。
同一个写法还潜伏在 Q5 的 copy 型社交按钮和游戏卡 UID 上。

现在的约定：反馈只落在显式标了 `[data-copy-hint]` 的元素上，其余节点一个字不动；
Toast 只说「已复制 QQ」，不回显账号。`tools/verify-copy.js` 逐条守着这些约定。

手机上介绍文字压到 2~3 行 —— 一屏要同时装下头像、名字、四张卡片、两个按钮，
简介是"补充"而不是"必须"。

## 三之二·五、Q2「在听」：自动同步网易云

### 要三样数据，来自三个接口，权限各不相同

| 要什么 | 接口 | 权限要求 |
| --- | --- | --- |
| 累计听歌数、等级 | `GET /api/v1/user/detail/{uid}` | ✅ 不用登录 |
| 听歌排行 | `GET /api/v1/play/record?uid=&type=1` | ⚠️ 不用登录，但要**账号把排行设为公开** |
| 我喜欢的音乐（兜底） | `GET /api/user/playlist?uid=` + `/api/v1/playlist/detail?id=` | ✅ 不用登录，也不用任何设置 |

> 旧文档里的 `/api/user/detail?uid=` 已经 404，只剩上面那个 `{uid}` 路径写法。
> `type=1` 是最近一周，`type=0` 是所有时间。

#### 一个长期被误解的错误码：`-2 无权限访问`

**它不等于"缺 cookie"，它的意思是"这个账号把听歌排行设成了私密"。**

验证方式：同一时刻、同一请求头，对不同 uid 发同一个请求 ——

| uid | 返回 |
| --- | --- |
| 2116、83659385、46665989…（普通用户） | `code=200`，`weekData` 有 19~100 条 |
| 1（网易云官方）、1695307327（本站） | `code=-2` |

如果真是"接口要登录"，应该是**所有** uid 都 `-2`。有账号能匿名读到，
说明这个接口本身是开放的，`-2` 是账号级隐私开关。

所以：**去 网易云 → 设置 → 隐私 → 打开「公开我的听歌排行」，就不需要 cookie 了。**

#### 代价：匿名读到的次数被脱敏了

服务端会把 `playCount` 置为 0，真实信息挪到 `score` 字段，
而 `score` 是**百分制相对热度**（实测 top1=100，其次 75、50、50、25…），不是绝对次数。

我试过所有能想到的绕过方式，都拿不到真实次数：

- `weapi`（AES-128-CBC ×2 + RSA 裸加密，协议本身完全跑通，返回合法 JSON）
- 移动端 UA + `os=android; appver=…`
- 桌面 UA + `os=pc; appver=8.9.11`
- `type=0`（全部时间）与 `type=1`（本周）都试
- 翻页 `limit` / `offset`（无效，始终返回 100 条上限）

结论：**脱敏是服务端设计，不是协议问题**，真实次数属于账号私密数据。
所以前端分两条路渲染：有真实次数就印「128 次」，只有热度就画一根归一化细条 ——
**绝不在只有 score 的时候印「100 次」**，那是编出来的数字。

#### 三层降级：页面上永远有真实内容

```
① 听歌排行（账号设为公开时）
      ↓ 拿不到（-2 私密 / 没记录）
② 我喜欢的音乐（零设置，默认公开，详情接口给前 6 首）
      ↓ 也拿不到
③ 上一次的数据（沿用旧 JSON，不擦空）
```

这就是为什么**什么都不配也能看到真实歌曲** —— 当前线上走的就是第 ②层，
页脚会如实标成「已同步 · 收藏」，不冒充排行。

### 为什么还需要一个仓库里的定时任务

因为浏览器端做不到跨域抓网易云（CORS 会拦），也带不了 `MUSIC_U`。
GitHub Pages 是纯静态托管，没有服务端能替你转发。所以流程是：

```
GitHub Actions（每天 10:10）→ 抓（不带 cookie 也能抓前两层）→ 写 data/netease.json → 提交回仓库
                                                                              ↓
                                                 页面加载后 sync.js 悄悄 fetch 这个 JSON
```

> 三层都在服务端抓，好处是**结果被固化进仓库**：即使网易云改接口、
> 或者某天请求失败，页面用的仍是最后一次成功的数据，不会变空。

### 专辑封面墙 + 磁贴（Q2 的视觉）

2026-11-11：黑胶彻底去掉，换成**这周听的 100 首歌的专辑封面**铺满整屏。

⚠️ 封面墙必须是 `#listen` 的**直接子元素**。第一版放在 `.listen-card` 里，
结果只盖住卡片那一小块；而 `.listen-card` 当时还是一整块实底板，
把封面挡得只剩边缘。现在容器透明、磁贴各自带实底、标题用光晕。

**结构与运动**（`assets/js/albumwall.js`）：

| 项 | 值 |
| --- | --- |
| 实例 | `2400×2400px` 固定，整体 `scale = max(W/2400, H/2400) × 1.05` |
| 格子 | `400×400` 正方形封面，6 行 × 每行单份 6 张 |
| 循环 | 每行渲染**两份完全相同**的图组（12 张 / 4800px） |
| 方向 | **1/3/5 行左移、2/4/6 行右移**，各行速度倍率还不同 |
| 驱动 | **纯 CSS 合成器动画**（`animation` + `translate3d`），主线程零开销 |
| 轮换 | ISO 周数做种子打乱 100 首，每周一零点自动换一批 |
| 离屏 | `IntersectionObserver` 置 `data-paused` → `animation-play-state: paused` |

无缝循环：每行 X 位移限制在 `[-2400, 0]`，内容占 `[0, 4800]`，
任意 X 都完整包住实例 `[0,2400]`；X 走到端点归位时两份内容相同，画面接得上。

**封面尺寸**：列表用 `?param=120y120`（34px 缩略图），
背景把同一 URL 换成 `?param=400y400`（约 10~60KB/张），不用再抓一次接口。
100 张全部探测过可用。

**缝隙**（用户专门点名的两块）：

- 图片之间：`display:block` 去掉 inline 基线缝、`gap:0`，
  每格宽高多 2px 再用 `margin-right:-2px` 收回占位 —— 相邻格**重叠**，
  缩放产生的亚像素亮线被盖住，而循环周期仍精确等于 2400。
  实测相邻图片间隔 **-1.26px**（重叠），不是缝隙。
- 上下交接：图片高度同样多出 2px，溢出到下一行顶部；
  行底再加一条 9px 的极淡羽化带，把行与行的硬切变成过渡。
  实测行间 gap 为 0。

**为什么用 CSS 动画而不是 rAF**（实测逼出来的）：

第一版用 `requestAnimationFrame` 每帧写 6 个 4800px 宽图层的 `transform`。
停在「在听」页时主线程被占满，帧率掉到 30fps（`verify-drag` 的 p50 从 16.7ms
变 33.3ms）。改成 `animation` + `translate3d` 后由合成器线程驱动，主线程一帧都不用管，
同样 6 层在动也不再和滚动、点击抢时间。

> 排查时有个反直觉的发现：**暂停动画也没让帧率回来**（仍 33.3ms），
> 只有减少渲染行数才回到 16.7ms。说明瓶颈是「6 层全屏图片的静态合成」，
> 在**无头浏览器（无 GPU、纯软件合成）**下必然如此，与动画无关，也不是代码退化。
> 所以 `verify-drag` 里那条帧率断言从"绝对值 ≤18ms"改成了
> **相对比较**（光效显示 vs `display:none`），它本来要证明的就是"光效没有额外开销"。
> 用绝对值量到的其实是运行环境的显卡能力。

**可读性**：不垫底板（会挡住封面）。标题 / 副标题 / 页脚用三层
`text-shadow` 光晕（`var(--bg)`，自动跟主题走），磁贴用 94% 实底。
遮罩只在上下边缘压实，中间保留 40% —— 第一版压到 58~76%，
截图里整面墙几乎全白，等于白做了。

自检 `verify-albumwall.js`（40 项）守：6 行方向、每周种子稳定、
相邻图片重叠、行间 gap 0、循环取模、三种视口覆盖、减少动效静止。

### 磁贴排版

- **封面**：每块磁贴左侧一张 34px 方图，尺寸写死（`width`/`height` 属性 + CSS），
  图片没到之前也不会把行高挤塌 —— 行高一变，`paged.js` 量到的落点就偏。
- **磁贴**：94% 实底（背景换成彩色封面后从 86% 提上来的）。
  不用 `backdrop-filter` —— 它是整屏级模糊，滚动时会掉帧。
- **网格**：桌面 3 列（6 首正好两行）、平板 2 列、手机 1 列。
  手机上若用 2 列，每块只有 165px，曲名会被截成 8 个字 —— 而曲名是这一屏的正文。
- **落单的磁贴通栏**：4 首或 5 首时最后一格横跨整行，避免右边留缺口。

### 站内播放：能播的只有一半，所以必须提前探测

网易云有个"外链播放"地址：

```
https://music.163.com/song/media/outer/url?id=<歌曲id>.mp3
```

免费曲目会 302 到真实 mp3（`audio/mpeg`），浏览器里可以直接 `<audio>` 播放。
但 **VIP / 付费专辑的版权曲返回的是一个 HTML 提示页**（"因版权要求无法播放"），
HTTP 状态还是 **200**。所以"能不能播"不能靠 URL 判断。

实测本站 100 首：**56 首能播、44 首不能**（听的日系曲子大多要会员）。
而且排行前 6 首里常常只有 1 首能播 —— 这个比例决定了 UI 必须诚实：

| 数据里的 `playable` | 渲染成 | 点下去 |
| --- | --- | --- |
| `true` | `<button data-play>`（强调色） | 就地播放 / 暂停 |
| `false` | `<a class="track__go">` | 打开网易云，`title` 注明"需要会员" |
| 未定义（老数据） | `<a>` | 同上 —— 保守，总比放个按不出声的按钮好 |

`scripts/sync.mjs` 里的 `canPlay()` 用 **Range 请求取头 2KB 看 Content-Type**，
并发 6 路。不用 HEAD：那条 302 链上的 CDN 对 HEAD 响应不一致，实测有误判。
探测结果写进 `data/netease.json` 的 `playable` 字段，前端只读不算。

页脚会在"部分可播"时补一句 `1/6 可试听`（完整原因在 `title` 里）。
全可播或全不可播都不显示 —— 那两种状态不需要解释，
偏偏"部分可播"最容易让人困惑："为什么第 4 首能放，第 1 首点了却跳走？"

播放器本身（`assets/js/player.js`）三条约束：

- **单例 `<audio>`**：换歌是换 `src`，不是新建元素。多首叠着响是最典型的 bug。
- **事件委托在 `#trackList` 上**：列表是 `innerHTML` 重建的，
  逐个绑事件会在第二次渲染后全部失效（这正是之前"看得见点不动"那类坑）。
- **播不了就认**：`error` 事件里复位界面、标 `is-blocked`、跳网易云。
  版权状态可能在两次同步之间变化，探测说能播不代表永远能播。

`config.music.src` 里如果填的是**网页地址**（`music.163.com/#/song?id=…`），
`live.js` 不会把它塞进 `<audio>`（必然报错、点一下会弹新标签页），
而是直接渲染成链接 —— 判断依据是扩展名或 `/media/outer/`。

### 一块磁贴的排版：两行网格

```
┌──────┬────────────────────┬────┐
│      │ 反方向的钟          │ ▷  │   ← 第一行：曲名拿到全部宽度
│  01  ├────────────────────┼────┤
│      │ 周杰伦 · 范特西     │128次│  ← 第二行：副标左、次数右
└──────┴────────────────────┴────┘
```

播放次数**放在第二行右侧**，不挤进第一行 —— 320px 的两列里每块只有 123px，
再分给次数 34px，曲名连四个字都放不下。序号跨两行居中，竖排仍然整齐。
`.track__main` 用 `display: contents` 把曲名和副标提升成网格项，DOM 不用改。

> ⚠️ 手机块里那条 `.track { padding: 9px 11px; column-gap: 10px; row-gap: 1px; }`
> **必须分开写 column-gap / row-gap**。写成 `gap: 10px` 会同时把行距设成 10px，
> 两行文字之间空出 10px，六行就是白白多出 60px —— 390×844 立刻从 roomy 掉到 tight。

### 一屏放几首，是按高度算出来的

真实排行有 6 首，而示例数据只有 3 首 —— 这个差别藏了很久：
320×568 上六行单列会把第二屏撑到 787px（超屏 219px），
paged.js 只好把**整站**降级成可滚动。

所以曲目数不是写死的 `limit`，而是 `render.js` 里 `trackCap()` 按视口倒推：

```
rows = round((视口高度 - 350) / 84)     // 350 = 页头 + 卡片内边距 + 页脚
曲目数 = rows × 列数                     // 列数由宽度决定（1 / 2 / 3）
```

350 和 84（磁贴 75px + 间距 8px）都是在真浏览器里量出来的。
**改了磁贴的内边距、字号或行距，这两个数要重新量** —— 否则又会撑破一屏。

| 机型 | 曲目数 | 档位 |
| --- | --- | --- |
| 1440×900 桌面 | 6（3 列 × 2 行） | roomy |
| 390×844 | 6 | roomy |
| 375×667 | 4 | roomy |
| 320×568 | 3 | snug |

想微调：`blocks.css` 里的 `.albumwall*`（实例规格/遮罩/缝隙）和 `.track`（磁贴外观）。
改主题色后遮罩与文字光晕会自动跟随，不用写两套。

### 配置步骤

#### 第 0 步就能用了（什么都不配）

只要 `config.js` 里填了 `listen.neteaseUid`，定时任务就能抓到：

- **累计听歌数**（不用登录）
- **我喜欢的音乐**前 6 首（不用登录，也不用任何设置）

#### 想要真正的「听歌排行」：只需改一个隐私开关

1. 打开 `music.163.com` → 右上角设置 → **隐私设置**
2. 打开 **「公开我的听歌排行」**
3. 等下一次定时任务跑（或 Actions 页面手动 Run workflow）

**不需要 cookie。** 代价见上文：匿名读到的次数是百分制热度，不是绝对次数，
页面会画成一根热度条而不是「N 次」。

#### 想要真实播放次数：才需要 cookie

1. 在 `music.163.com` 按 F12 → Network → 随便点一个请求 → 复制 Request Headers 里的
   完整 `Cookie`（重点是有 `MUSIC_U=...` 这一段）
2. Settings → Secrets and variables → Actions：
   - 新建 **Secret** `NETEASE_COOKIE`，粘贴整串 cookie
   - 新建 **Variable** `NETEASE_UID`，填数字 UID（也可以跳过，直接用 config.js 里的）

4. **手动跑一次**
   Actions → `Sync external data` → Run workflow。几十秒后 `data/netease.json` 会被提交。

之后每天自动跑一次。

### 同一个工作流里的 Steam 那一步

`sync.yml` 除了网易云，还会跑一次 Steam 的 API-only 同步（`node scripts/sync-steam.mjs --api-only`），
用来更新游戏战绩和「最近入库」。要开它只需一个 Secret：

- **Secret** `STEAM_API_KEY` — Steam Web API 密钥（免费领：<https://steamcommunity.com/dev/apikey>）

没配也不会失败：那一步会打一行提示后跳过，`data/steam.json` 保持上一次本机抓取的结果。
封面墙（`apps` / `portraitApps`）只能在本机用真实浏览器抓，CI 不碰那两块 ——
详见「三之二·六」里的两种跑法对照表。

> 为什么密钥要放 Secret 而不是写进代码：提交进 git 历史里的密钥等于公开。
> 本机跑的时候用 `steam-key.txt` 或环境变量，那个文件已经在 `.gitignore` 里。

### 抓不到会怎样

**页面不会坏。** 三层保护：

| 情况 | 表现 |
| --- | --- |
| 没配 cookie / cookie 过期 | 排行降级到「我喜欢的音乐」，**累计听歌照常更新** |
| 三层都失败 | `data/netease.json` 里 `tracks` 为空，前端用 `config.js` 的 `listen.fallback`，页脚照样显示累计听歌 |
| 网络错误 / JSON 损坏 | `sync.js` 静默降级，控制台不报错 |

脚本会把两个接口分别处理：**累计听歌拿到就写，排行拿到就写，互不牵连**。
早先只有一个接口，cookie 一缺整个 JSON 都写不出来，页面上是一片示例数据 ——
而累计听歌本来不需要登录，白丢了。

cookie 大约 3~12 个月会失效。失效后页面会停在最后一次成功的数据上，
底部状态会从「已同步」显示成「示例数据」，这时重新存一次 cookie 即可。

### 关于「主页缩略图」

网易云 / 闲鱼 / 小黑盒三个站都是单页应用，服务端只返回空壳 HTML，
抓不到 `og:title` / `og:image`（实测拿到的是「网易云音乐」「闲鱼 - 闲不住？上闲鱼！」
这种平台品牌标题，写进页面只会更差）。所以**缩略图请自己截图**：

1. 截图存成 `assets/img/netease.jpg`（建议 16:9，宽度 800px 左右，几十 KB）
2. `config.js` 里把对应卡的 `cover` 填成 `"assets/img/netease.jpg"`

填了 `cover` 就显示成带封面的缩略图卡；留空则是纯文字信息卡 —— 两种都好看，
不必为了"有图"而放一张模糊的截图。

## 三之二·六、Q3「游戏」：一块战绩板 + 一面会动的封面墙

分三块，各管一件事：

| 块 | 谁渲染 | 数据从哪来 |
| --- | --- | --- |
| **战绩板**（顶栏 + 三格汇总 + 游戏列表 + 最近入库） | `render.js` 的 `renderGaming()` / `renderGameStats()` | `config.js` 的 `gaming.items` + `data/steam.json` 的 `lib` / `recent[]` / `added[]` |
| 斜 45° 封面墙 | `steamwall.js` | `data/steam.json` 的 `portraitApps` |

> 2026-11-11 用户要求：**只留 Steam**（明日方舟 / 无畏契约先下线），
> 并且要像小黑盒那样显示「游戏时长 + 成就」。下线用的是 `hidden: true`，
> 数据都还在，把那一行删掉就回来。
>
> 同一轮还定了一件事：**整块战绩板是一个 `<a>`**，点哪都进 Steam 主页。
> 早先那个「点一下复制好友码」的按钮已经删掉 —— 好友码只剩展示。
> 因为整块是链接，板子里**不能再套任何交互元素**（嵌套 `<a>` 是非法结构，
> 点击会打架）。`verify-gaming.js` 有一条断言专门守这个。

### 战绩列表：数据怎么来的（以及怎么变成全量）

`scripts/sync-steam.mjs` 有两条路，**有 key 走 API，没 key 退回公开资料页**：

| | 有 `STEAM_API_KEY` | 没有（当前默认） |
| --- | --- | --- |
| 游戏数量 | 全库（`game_count`） | 库存解析出的数量（只含带卡牌的游戏，偏少） |
| 游戏时长 | 全库总时长 | **只有最近几款的和** |
| 最近两周 | ✅ | ✅ |
| 成就 | ✅ 每款 x/y | ✅ 最近几款 |
| 页面标签 | 「游戏时长」 | 「近 N 款时长」（`lib.partial` 为真时） |

要全量数据，去 <https://steamcommunity.com/dev/apikey> 领一把免费的 key
（随便填个域名即可），然后二选一：

```bash
# ① 临时用
STEAM_API_KEY=你的key node scripts/sync-steam.mjs

# ② 长期用（文件已在 .gitignore 里，不会进仓库）
echo 你的key > steam-key.txt
node scripts/sync-steam.mjs
```

> 为什么公开页只给几款：`/profiles/<id>/games?tab=all` 现在要登录才给看，
> 而不登录能看到的是资料页的「最新动态」—— 就几款。

### 两种跑法：本机全量 / CI 只跑 API

库存抓取（`apps` / `portraitApps`，封面墙用的那两份）**必须真实浏览器**：
裸 TLS 请求会被挡，差异在 TLS 指纹不在 IP。所以那条路只能在有 Chromium 的机器上跑。

但「游戏库统计 + 最近入库」只依赖 Web API，不需要浏览器。为此有第二个模式：

```bash
node scripts/sync-steam.mjs --api-only
```

| | `node scripts/sync-steam.mjs` | `--api-only` |
| --- | --- | --- |
| 需要 Chromium | 是 | 否 |
| 抓库存 / 封面墙 | ✅ | 跳过，**沿用上次结果** |
| 战绩（数量 / 时长 / 成就） | ✅ | ✅ |
| 最近入库（差集） | ✅ | ✅ |
| 能跑在 GitHub Actions | ❌ | ✅ |

CI 里就是这样跑的（`.github/workflows/sync.yml`，Secret `STEAM_API_KEY`）。
`--api-only` 拿不到数据时**直接退出、不写文件** —— 宁可这一天没更新，
也不能把已有的封面墙和 `added` 记录冲成空。

### 「最近入库」：为什么需要自己记账

Steam 的 `IPlayerService/GetOwnedGames` 里**没有"购买时间"字段**。
唯一沾时间的是 `rtime_last_played`，那是"最后游玩"。所以要回答
「最近入库了什么游戏」，只能靠**两次同步的 appid 差集**：

```
第 1 次同步 → 全库 appid 存成基线（owned），不产出任何记录
第 N 次同步 → 本次全库 − 基线 = 这期间新入库的 → 追加到 added（新的在前）
            → 基线换成本次全库，下次继续比
```

这意味着两件事：

1. **必须按天跑**。断一天，那天入库的游戏要等到下一次同步才会被发现
   （它不会丢，只是日期记成发现那天）。
2. **第一次跑只有基线**。不这么做的话，143 款会一次性全变成"新入库"，
   页面变成一堵墙。

这条逻辑独立在 `scripts/lib/steam-added.mjs`，是**纯函数**（没有网络、没有文件、
没有时钟，`today` 由调用方传入），所以能被 `tools/verify-steam-added.js`
用假数据把全部分支跑完：首次建基线 / 无变化 / 新增一款 / 连续累积 /
超 12 条截断 / 重复 appid / 空库不清记录 / 旧版 JSON 缺字段。

| 字段 | 含义 |
| --- | --- |
| `owned[]` | 上一次的全库 appid 快照（下次同步的基线，前端不用） |
| `added[]` | 最近入库，`{appid, name, at}`，新 → 旧，最多 12 条 |
| `ownedSince` | 基线建立日期。`added` 为空时前端用它说"从 X 日起没添新游戏" |

前端只把 `added` 铺成一条横向封面带（最多 8 个 + `+N`）。封面的取法和列表一样
走 `cover` 字段，抓不到就退到色相渐变块，不会出现空黑框。

### 战绩列表的版式（改之前先读这段）

```
┌────────┬──────────────────────────────────────────┬────────┐
│ 封面   │ 游戏名                                    │  🏅    │
│ 16:9   │ 2,491h ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓░  28h              │ 12/12  │
└────────┴──────────────────────────────────────────┴────────┘
```

- **时长条**是 √ 归一化的（不是线性）：库里 2491h 与 2.7h 差 900 倍，
  线性会让除第一名外全塌成 1px。所以改分母不影响"相对长短"的语义。
- **条的颜色**由 appid 哈希出色相（`hueOf`），每款一个色，只用来分开相邻行，
  不承载信息 —— 和小黑盒一样。
- **只有全成就**才给那枚奖章 + 强调色数字。没打满只写 x/y。
- 抓不到数据时整块 `hidden`，不留空标题。
- **行数上限 30**：数据端（`sync-steam.mjs` 的 `ROWS`）只抓 30 行，渲染端
  （`render.js` 的 `ROW_LIMIT`）也只画 30 行。两处必须一致，否则一边白做。

### 「查看全部」为什么不许压住最后一行

它是 `position:absolute; bottom:0`，锚在**板子底边**上，高度 46px（渐隐 + 一行字）。
算 `max-height` 时有三个容易踩的坑，都踩过：

1. 让出的高度要对。早先写死让 26px，而它实际 46px —— 每屏都压掉最后一行 20px。
2. `max-height` 是 **border-box**，列表的 1px 上边框也在里面，要加回来。
3. **方向是反的**：把 `max-height` 调小，板子跟着变矮，条也跟着上移 ——
   等于没让。要让它让开，只能把列表**加高**，把条往下推。

所以最终写法是 `visible * rowH + strip + borderH`，并且在行落地后再用**实测行高**
重算一次（MiSans 分片加载会让行高从 63.25 变成 64），最后按"第 visible 行的实际
底边 vs 渐隐顶边"补齐亚像素差。`verify-gaming.js` 在桌面 / 平板 / 手机三档都断言
"压住 0 行"。

### 滚动行与翻页手势：边界在哪

翻页接管的是**整个窗口**的竖向手势（触摸 + 滚轮），而 `.gb-list` 自己也是竖向滚动的。
不划界会变成：手指在列表上划 → `preventDefault` 掐掉原生滚动 → 抬手时又被当成翻页，
**想滚列表结果翻走一屏**（实测线上旧版：列表 scrollTop 纹丝不动，页码 2→3）。

现在的判据只有一条，在两个入口共用（`paged.js` 的 `scrollOwnerOf` / `canScrollBy`）：

> 手势起点所在的可滚动祖先，**还能朝这个方向滚**，就整段让给浏览器；
> 滚到头了，下一划才翻页。

实测：列表内上划 → 列表滚 252px、页码不动；滚到底再上划 → 翻页；空白处上划 → 翻页。

### 渲染分块：每块独立渲染、独立报错、可单块调试

`render.js` 的初始化不是 9 个 `renderXxx()` 直调，而是一张块表
（`theme / sections / meta / brand / profile / listen / gaming / repair / links / contact / controls`），
按 layer 从低到高跑（骨架 → 文案 → 内容 → 控件）。

每条都单独 `try/catch`：**一块抛错不再带走整页**，并且会在自己的容器上留
`data-render="ok|error"`（失败还带 `data-render-error="原因"`）——
DevTools 里一眼看出是哪块没画出来，不用猜。

排查用的三个入口：

```js
SITE_RENDER.report()          // 每块的成败与耗时（毫秒）
SITE_RENDER.renderOnly('gaming')   // 只重画某一块
// 或者打开页面时：?render=gaming,listen   只渲染这几块
```

### 安卓 Edge / Chrome 的「自动深色」必须显式关掉

实机（Redmi K80 + 安卓 Edge 156）上出现「游戏列表整块空白」，探针读到的数据是：

```
data-theme = light      --text = #17191b      --bg-elev = #ffffff
.gb-row 存在 30 条、opacity 1、高 63px，文字色 rgb(23,25,27)
```

页面自己的配色明明是**浅色**，屏幕上却是深色 —— 说明浏览器做了 **force dark**（自动深色）。
它按像素反色，且**不认 CSS 变量**：`.gb-list` 带 `mask-image`，反色会跳过这类元素，
于是深色底 + 没被反色的深色文字 = 整块列表「消失」。顶栏图标发灰、头像发暗也是同一个原因。

修法：在首帧前声明本页自己管配色（`only light` / `only dark` 是官方的退出方式）：

```js
// index.html 内联脚本 + skin.js 的 apply()
root.style.colorScheme = mode === "dark" ? "only dark" : "only light";
```

两个位置都要写：内联脚本负责首帧（否则会先被反色闪一下），`skin.js` 负责之后每次换主题。

### 预取闸门：第一二屏缓存完才进站（`assets/js/preload.js`）

> **默认关闭**（`config.js` 的 `live.preload: false`）。它会让首访多等 1~4 秒，
> 排查渲染问题期间不该再叠这个变量。需要时改成 `true`，或在 URL 上
> 加 `?preload=1` 临时开启 / `?preload=0` 强制关闭。

站点本来就是「一屏一页」，但第 2 屏的背景是 144 个相册封面、第 3 屏是 48 张游戏封面。
它们和首屏抢同一条带宽、同一份解码内存 —— 移动端上足以让首屏内容迟迟画不出来。
所以加了一道闸门：

| 时机 | 行为 |
| --- | --- |
| 这台设备**第一次**来 | 复用 splash 当闸门：第 1、2 屏的图**全部 decode 完**才放行，底部那条细线显示真实进度 |
| 放行之后 | 立刻并发预取第 3 屏（不阻塞，失败无所谓） |
| 回访（版本未变） | **不等**，直接进站；只对没进缓存的图做一次暖机 |
| 回访（版本变了） | 也不挡人（换批封面不该让老用户多等），后台补图并更新版本号 |
| CDN 抽风 / 图全 404 | 到点就放行 —— 预取失败绝不能把人锁在门外 |

**版本号怎么算**：把三屏图片的**绝对 URL 排序后**做 FNV-1a。三个坑都踩过：

1. 用 `currentSrc` 会让同一张图产出两种字符串（已加载=绝对、未加载=相对），
   版本号在两次访问间乱跳 → 只读 `src` 属性并 `new URL()` 归一化。
2. 收集时机不能靠 `data-ready`：两面墙、战绩列表各有各的异步来源，
   先到先得会让集合不同 → 改成**自稳定探测**（URL 集合连续 300ms 不变才算定下来）。
3. 总时限必须从脚本执行那一刻算，否则最坏是「等 DOM 2.5s + 等图 4.5s = 7s」。

**`load()` 里两个必踩的坑**（都修了）：`new Image()` 只被局部变量引用会被 GC、
请求取消后 `onload` 永远不来（要用 pool 持有到结束）；`onload` 与 `decode()` 都会回调，
必须用 `done` 标记只结算一次，否则提前 resolve。

自检：`node tools/verify-preload.js`（17 项，覆盖冷启动 / 回访 / 版本变化 / 图全挂）。

### 封面墙为什么不能懒加载

`loading="lazy"` 看着很合适，实测**不能用**：整面墙 48 个 `<img>`，被
`.steamwall` 的 `overflow:hidden` 裁掉的那些会被判成"还不需要"，于是永远不加载，
只有 20/48 张到位，剩下 28 格露出 `--h` 纯色块 —— 墙看起来是花的。

保留的是 `fetchpriority="low"`：它不影响"加不加载"，只把背景图排到首屏数据后面，
减少弱网下的管道争抢。这是在不改变画面的前提下唯一安全的一档。


这一屏的用途很单一：**让人一眼看到我在玩什么、玩了多久，顺手点进 Steam**。

早先每张卡有 `note`（一句备注）+ `stats`（三项「可展现资产」）+ 区服段位，
一屏只能放 4 个游戏，而且没人会读简介。2026-11-11 又收了一次：
Apex / DJMAX / Phigros / 中二节奏 四张卡合进一张 Steam 卡 ——
访客真正会做的事只有两件：加手游好友、翻我的 Steam。

现在板子里只剩顶栏那一行：图标 + 平台名 + 平台标签 + 好友码 + 箭头。
好友码是**纯文字**，不是按钮 —— 要加好友的人自己会复制，不需要一个"复制成功"
的 toast 来打断浏览。

| 字段 | 说明 |

### 用自己的游戏图标

1. 图片放进 `assets/img/`，建议正方形、128×128 以上、PNG 或 WebP
2. `config.js` 里给对应游戏填 `iconImage: "assets/img/arknights.png"`

编辑器里也能填（「游戏」页 → 自定义图标图片地址）。图片路径是相对站点根目录的。

### 怎么加游戏

`config.js` 的 `gaming.items` 里加一项即可。**第一项会被渲染成整块战绩板的顶栏**
（图标 / 名字 / 标签 / 好友码 / 箭头），第二项起进了 `hidden` 就不会上屏。
2026-11-11 之后 Q3 不再是「每款游戏一张卡」，所以不存在"加卡把一屏撑破"的问题 ——
游戏是 `data/steam.json` 里的行，行数由屏幕高度决定（详见上面的版式一节）。

> 当前的 UID 都是示例，请换成你自己的。留空 `uid` 时顶栏不显示好友码那一段。

### Steam 卡：`steam` 字段

| 字段 | 说明 |
| --- | --- |
| `steamId` | 17 位数字 ID（好友码），卡片上显示的就是它 |

### 封面墙：固定大实例 + 整体等比缩放

2026-11-11 按截图重写。旧版是「按 170%/200% 百分比给网格、横版 header.jpg、
靠滚动位置驱动位移」，实测三个端口全不合格：右下大片空白、手机上几乎全空、
斜拼有白线、停在这一屏时位移只有 -0.04% 等于不动。

现在按「**实例做够大，再对整个实例等比缩放**」来做：

| 项 | 值 | 说明 |
| --- | --- | --- |
| 实例 | `2400×2400px` | 固定设计像素，与设备**完全无关** |
| 格子 | `400×600px` | 2:3，正好是竖版封面比例，不裁切 |
| 排布 | 6 列 × 每列 8 格 | 8 格 = 两份相同的 4 格，用于无缝循环 |
| 倾斜 | `rotate(45deg)` | 顺时针 = 竖版封面向右倾 45° |
| 缩放 | `√2 × max(W,H) × 1.12 / 2400` | JS 算好写进 `--wall-scale` |

覆盖公式：一个 `S×S` 正方形旋转 45° 后，能完整内接的轴对齐正方形边长是
`S/√2`。撑到 ≥ `max(W,H)` 就盖得住四角。实测：

```
1440×900   → scale 0.950，内接 1613px
390×844    → scale 0.557，内接  945px
1920×1080  → scale 1.267，内接 2150px
820×1180   → scale 0.779，内接 1322px
```

同一套布局、同一个格子数，只是整体放大倍率不同 —— 换设备不会再缺一角。
`gap: 0` 且 `border-radius: 0`：斜着拼时任何间隙都会变成显眼的白色菱形线，
圆角则会在四格交界留下小三角底色。

**为什么永远填得满**：每列渲染两份**完全相同**的 4 格图组（高 4800px），
从 `top = -2400` 起放。位移 `d ∈ [0,2400]` 时，内容覆盖
`[-2400+d, 2400+d]`，恒包住实例 `[0,2400]` —— 上沿 ≤ 0、下沿 ≥ 2400 永远成立。
`d` 从 2400 归零时，两份内容相同，画面接得上，看不出跳变。

**为什么现在真的会动**：改成时间驱动的持续流动，不再依赖 `scrollY`。
每列 `d = (phase × 倍率) % 2400`，`phase` 由 rAF 按 `48px/s × SPEED` 累积。
翻页站点停稳后滚动位置不变，靠滚动进度驱动的视差必然归零 —— 这正是旧版
"看着像不能滚动"的根因。滚动时另叠一个会衰减的 `boost`，翻页瞬间会跟着冲一下。

倍率仍用正弦分布 `0.55~1.45`（随机会让相邻列一快一慢像抖动，正弦是连续变化，
读起来像流动）。位移只写 `translate3d(0, y, 0)`，X 恒为 0。

**格子尺寸是性能调出来的**。第一版用 `300×450 / 8 列 / 每列 12 格 = 96 个 <img>`，
`verify-perf` 的滚动帧耗时从 61ms 翻倍到 118ms —— 96 张 600×900 竖图在软件合成下
要维护约 52M 像素纹理。放大到 `400×600` 后变成 `6 列 × 8 格 = 48 张`（砍半），
覆盖面积一点没变，手机上单张反而更清楚，帧耗时回落到 72ms。

另外用 `IntersectionObserver` 在游戏屏离屏时**把 rAF 整个停掉**。
早先是在 tick 里每帧读 `getBoundingClientRect()` 判断"离得远就跳过"，
那样即使离屏也保持一帧一次的调用，而读 rect 本身会触发强制布局。
`rootMargin` 只留 0.3 屏 —— 留一整屏的话 gaming 作为第三屏在首页就算"可见"，
等于没优化。

调速度：

```js
SITE_STEAMWALL.setSpeed(2);   // 控制台现场试，0 = 静止，范围 0 ~ 6
```

或改 `config.js` 的 `gaming.items[].steam.scrollSpeed`。

### 封面必须是竖版，且必须逐张验过

封面走：

```
https://cdn.cloudflare.steamstatic.com/steam/apps/<appid>/library_600x900.jpg
```

**不是** `header.jpg`（460×215 横版）。每张 38~77KB，2:3 正好铺满格子。

⚠️ 库存里 45 个游戏 appid 有 **8 个没有竖版封面（404）**。不剔掉就会在墙上
开天窗，正是旧版露白的原因之一。所以同步脚本会逐张探测（状态码 200 且 >5KB），
把结果写进 `data/steam.json` 的 `portraitApps`（实测 37 张可用），
前端只用这一份；`apps` 保留完整清单供别处引用。渲染层还有 `img.onerror`
兜底，CDN 临时故障时用深色渐变顶上，绝不留白。

### 封面从哪来

公开库存 JSON，不需要登录、不需要 API key：

```bash
node scripts/sync-steam.mjs        # 需 playwright-core + 本地 chromium
```

脚本读 `steamcommunity.com/inventory/<steamid>/753/6`，对每件物品取
`market_hash_name` —— 形如 `"730-Trading Card"`，**前缀就是游戏 appid**，
去重后写进 `data/steam.json`。实测 280 件库存 → 74 个 appid（游戏 45 / 特卖活动 29），
再逐张验封面 → 37 张可用。

三个必须知道的坑：

1. **不能裸 TLS 抓**。`curl` 或 node 的 `fetch` 直连 steamcommunity.com 会超时，
   真实浏览器却 200 —— 差异在 TLS 指纹。所以脚本用 playwright 驱动浏览器，
   读 `document.body.innerText` 再自己 `JSON.parse`。
2. **`profiles/<id>/games?tab=all` 抓不到**。未登录会被重定向到登录页。
   库存接口是唯一匿名可读的入口（小黑盒走的就是这条）。
3. **753 是平台本体**，它的市场名没有 appid 前缀，必须跳过。

三级降级，墙永远有图：`portraitApps` → `fallbackApps`（12 个，都已验过有竖版图）
→ 不渲染。`prefers-reduced-motion` 下静止，但图还在、还是斜 45°。

### 文字可读性：不垫底板，让字自带光晕

试过两种"在标题后面垫一块半透明板"的做法，都被截图否掉了：
线性渐变在垂直方向均匀，露出一条**水平硬边**；改成径向椭圆，又被盒子
**左边缘**截断成一条竖硬边。而且底板本身就要挡住一块封面，和"完全填充"冲突。

最终给 `#gaming .section__head > *` 加三层 `text-shadow` 光晕
（`0 0 6/18/34px var(--bg)`）：紧致的一层护住笔画，扩散的两层把周围彩色封面
推开。颜色用 `var(--bg)` —— 浅色主题近白、深色主题近黑，自动跟主题走。
副标题另外提到正文色 + 半档字重（只有 Q3，其它屏维持原设计）。

自检 `verify-steam.js` 里有一组**像素级填充断言**：截「有墙 / 隐藏墙」两张图，
逐像素比对四角、边缘、中心的差异比例。实测四角覆盖率 76%~98%，
这是唯一能客观回答"背景有没有被封面填满"的办法 —— 肉眼截图守不住回归。

## 三之二·七、Q4「维修」：报价表 + 四步估价器

> **2026-11-11 起这一屏已下架**（`sections.repair.enabled = false`）。
> 下面整节的功能、代码与数据都完整保留，随时可以把开关改回 `true` 恢复；
> `verify-calc.js` 会临时展开隐藏的屏继续验证计算器代码，所以覆盖没丢。

### 报价表：闲鱼在售快照

`config.js` → `repair.quote`，结构和闲鱼主页一致 —— **一件在售物品一条**：

```js
{
  title: "闲鱼在售",
  note: "价格与成色以闲鱼页面为准，点条目可直达。",
  source: "snapshot",
  profileUrl: "https://www.goofish.com/",   // 右上角「去闲鱼看看」
  updated: "2026-11-11",                    // 快照日期，提醒自己该更新了
  items: [
    { title: "GPW 换欧姆龙蓝点", price: "¥60", condition: "在售", note: "含工时", url: "https://…" }
  ]
}
```

渲染规则（`render.js` 的 `renderQuote()`）：

- `url` 有值 → 整行是 `<a>`，点进闲鱼；没值 → 是 `<div>`，只做展示。
  **不写死 `<a>`**，否则没有链接的条目会被读屏念成一个点了没反应的按钮。
- `condition` 里含「已成交 / 售出」→ 整行降到 55% 不透明度，但**留在列表里**。
  成交价是信任来源，删掉反而像在藏。
- 摘要行显示「N 件在售 · 共 M 件」，两个数都从 `items` 现算。

为什么不自动抓闲鱼：想看别人的在售列表要有登录态，公开页面也没有可匿名读的接口
（和 Steam 那种「库存 JSON 公开可读」不是一回事）。所以这里是**手动快照**。

### 估价器：跳转式四步

```
① 种类 ──选完自动──▶ ② 项目 ──▶ ③ 方式 ──▶ ④ 加急 ──▶ 报价
  ▲                                                     |
  |_____ 上方一行「回执」：只显示上一步的答案，点它就回退 ____|
```

一次只问一件事，**选完立刻跳下一问**，没有「下一步」按钮。

- **没有进度条**。它一直提示「还有三步」，而这一屏的节奏本来就是一张一张来的。
  改成在问题上方留一行极简回执：只有刚答完的那一项，用来确认「刚才选的是这个」。
- **材料不再单独问**（原来是第三步）。标准件/高端件的差别已经在价格区间里，
  多问一屏就是多一次流失。默认走 `materialDefault`。
- 卡片高度四步一致（`min-height: 336px` + 项目号 `data-opts` 锁等高），
  否则下面两张卡会跟着一跳一跳。

算法（`assets/js/repair.js`）：

```
基准价 = 项目价 × 种类系数
估算值 = 基准价 × 材料系数 + 方式附加 + 加急附加
区间   = 估算值 × range[0] .. 估算值 × range[1]      // 默认 ±15%
```

`quote: true` 的项目（「复杂问题」）不报价：出结果时改说「需要先看一眼」，
并给一句引导，而不是印一个编出来的数字。

四处刻意的设计：

1. **输出区间而不是一个数**。实际维修总有浮动，报一个精确数字反而不可信。
2. **不适用项直接不出现**。`services` 上可以挂 `devices: ["mouse"]` 限制适用种类，
   选了别的种类这一步就只剩适用的那些 —— 一次只问一件事的时候，
   摆一堆灰按钮只会让人犹豫。设备还没选时给全量，不会出现空白步骤。
   > 当前业务数据里都是鼠标项目，所以一条 `devices` 都没挂；将来加「换轴」时
   > 填上 `devices: ["keyboard"]` 就行，代码一行不用改。
3. **换设备后项目可能被清空**。原来选的「换微动」键盘做不了，就清掉并重新问
   「要修哪一项」。清空而**不是**自动顶替 —— 自动顶替会让人以为自己选过。
4. **回头改答案直接出结果**。中途点回执改项目，改完不会把人又拖回后面的问题，
   而是直接给新价格 —— 他改这个就是为了看新数字。

选项底下那行小字（「官方件，最稳 · 系数 ×1」）不是装饰：它把 note 里的说明
搬到了明面上，手机上本来就没有 hover，这些信息以前等于没写。

系数和选项在 `config.js` 的 `repair.calculator`。

### 数据怎么扩展

四层结构全是数组，加业务不用改代码：

| 要加什么 | 改哪里 |
| --- | --- |
| 新种类（手柄、耳机） | `devices` 加一条，`factor` 是价格系数 |
| 新项目 | `services` 加一条；只对某几类适用就挂 `devices` |
| 新收件方式 | `methods` 加一条，`add` 是附加费 |
| 新时效 | `rushes` 加一条 |
| 新报价条目 | `repair.quote.items` 加一条 |

面板里的字段名是固定的（`devices` / `services` / `methods` / `rushes`），
`repair.js` 顶部的 `POOL` 就是这层映射 —— 注意 `rush` 要拼成 `rushes`，
不是 `rushs`。

### 无障碍

- 每组选项是 `role="group"` 里的一组按钮，选中态用 `aria-pressed`
- 跳转后焦点落在新的问题块上，读屏会先念问题；按 `Tab` 才进选项，
  不会因为「手一抖按到回车」替人选了一项
- 方向键只在组内挪焦点，**不**选中（这里一选中就跳步，用方向键浏览会变成连环跳）；
  `Enter` / 空格是原生按钮行为，选中并前进
- 价格区是 `aria-live="polite"`，读屏会播报新价格
- 没有 JS 时报价表照常可读，计算器位置显示一句降级说明

## 三之二·八、背景系统

### 两条封面墙的缩放：量的是区块，不是窗口

Q2「专辑墙」和 Q3「游戏墙」都是"固定实例 + 等比缩放"，`scale` 按
`max(宽, 高)` 反推。**这个宽高必须取自背景层自己的盒子**
（`wall.clientWidth/clientHeight`），不能取 `window.innerWidth/innerHeight`：

- 背景层是 `position: absolute; inset: 0`，跟的是区块的 CSS 高度（100vh / 100dvh）；
- `innerHeight` 是"当前可见高度"。iOS Safari 地址栏展开时它比 100vh 小 60~120px，
  安卓 WebView、"这一屏内容比视口高"的降级布局里也一样。

用小的那个数算 scale，实例就撑不满区块 —— 底部露一条底色。
2026-11-11 就是这条把手机上的两屏背景判成了"错"的。修完顺带加了
`visualViewport` 的 resize 监听：地址栏伸缩只改它，不一定发 window.resize。


背景是分层叠出来的，每一层都能单独开关：

```
页面底色 → 背景图片 → 遮罩 → 光晕 → 网格 → 微粒 → 噪点
（全部在内容之下，pointer-events: none，绝不挡点击）
```

### 四种动效元素（可任意叠加）

| 元素 | 观感 | 配置 |
| --- | --- | --- |
| **光晕** | 两团缓慢漂移的柔光，跟着主题色走（默认开） | `motion.aurora` |
| **噪点** | 极细颗粒，让大面积纯色不呆板（默认开） | `motion.grain` |
| **网格** | 极淡的参照线，偏工程感 | `motion.grid` |
| **微粒** | 缓慢上浮的星点，偏夜色感 | `motion.stars` |

网格间距、微粒浓度都能调。系统开启「减少动态效果」时，位移全部静止，只留静态纹理。

### 背景图片：4 套内置 + 可上传

内置的 4 张都是我手写的 SVG，**单个不到 1KB，零外部依赖**，放在 `assets/backdrop/`：

| 内置 | 观感 |
| --- | --- |
| 柔光 `mesh` | 三团叠加的柔和光斑 |
| 沙丘 `dunes` | 层叠的弧形山脊 |
| 地平线 `horizon` | 一条地平线加中心光晕 |
| 线格 `lines` | 规则网格加两个几何形 |

编辑器「背景」页可以点选，也能上传自己的照片（自动限宽 1920、压成 WebP）、或直接填外部链接。

### 可读性保护：这部分是重点

**背景图一旦压在文字下，对比度就不可控了。** 我没有靠"看着还行"，而是实测了 7 套主题 × 2 种明暗 × 最坏图片（浅色配纯黑、深色配纯白），用 WCAG 公式算真实对比度。

两层保护：

1. **遮罩层**：图片之上盖一层取自 `--bg` 的颜色，强度默认 0.65（可调 0.15–0.95）。因为取的是主题底色，切换浅色 / 深色时会自动跟着变。
2. **文字保护色**：光靠遮罩不够。实测浅色主题配黑图时，即使遮罩拉到 0.85，辅助小字（时钟、页码、卡片元信息）也只有 **3.19**，因为 `--text-3` 本身就浅。所以图片模式下额外把：
   - `--text-3` 向正文色混合 50%（小字从 2.63 提到 5.5+）
   - 背景上直接暴露的两处强调文字（`eyebrow` 小标签、首页身份行）改用向正文混合 45% 的主色（从 3.10 提到 5.6）

**只改这两类，卡片内和按钮上的主色完全不动**——因为它们有自己的实底色，不受背景影响。主题气质保住了。

实测最差组合（`paper` 浅色 + 纯黑图）：标题 11.16 / 正文 5.15 / 小字 5.52 / eyebrow 5.63，全部达标。

图片关掉后这些覆盖立即撤销，不影响无图时的观感。

### 其他细节

- **坏链自动退回**：图片先预加载，失败就静默退回纯色背景并在控制台留一行提示，绝不留下空白或半加载的灰块。
- **视差**：光晕跟鼠标（幅度 26px），图片跟滚动（反向，幅度 60px 以内），两者叠加才有前后层次。
- **Ken Burns**：可选，48 秒一个来回的极缓推近，静态图也有呼吸感。
- **打印**：背景层整体隐藏，省墨。

> ⚠️ 遮罩强度不建议低于 0.5。低于这个值，图片会和文字抢注意力，自检里的对比度断言也会失败——编辑器里那三个滑杆下方有实时预览，调的时候能直接看到文字是否还清楚。

## 三之三、指针与触控光效

四层，彼此独立：

| 光效 | 行为 | 生效条件 |
| --- | --- | --- |
| **全局追光** | 一团很淡的光缓动跟随鼠标，制造「有光源」的感觉 | 仅精确指针设备 |
| **卡片光斑** | 指针在卡片内时，光落在指针所在位置，不是固定居中 | 仅精确指针设备 |
| **触控涟漪** | 手指按下处扩散一圈，给即时反馈 | 仅触屏 |
| **拖拽光效** | 按住拖动时聚光团跟随 + 撒拖尾点 | 桌面与触屏都有（参数不同） |

光效都刻意做得很淡：`--accent-soft` 本身就是 9% 透明度的主色。光效是气氛，不该抢内容。

### 拖拽光效：两端参数不同

| | 桌面 | 触屏 |
| --- | --- | --- |
| 光团直径 | 180px | **280px**（指尖会遮住约 45px，必须做大） |
| 光团位置 | 正中指针 | **上移 36px**（让光露在指尖之外） |
| 跟随系数 | 0.38（慢一点更柔） | **0.62**（慢会显得"追不上"） |
| 撒点间隔 | 12px | 19px |
| 拖尾点径 | 14px | 12px |

按住时还会**暂时收起常驻追光** —— 两个光叠在一起会糊成一片。

### 这里有一个必须知道的手势陷阱

**在可滚动页面上，浏览器一旦判定为滚动手势就会发 `pointercancel`，之后 `pointermove` 完全停止。**

实测一次 12 步的竖直拖动：

| 事件 | 触发次数 |
| --- | --- |
| `pointermove` | **1** |
| `pointercancel` | 1 |
| `touchmove` | **9** |

所以如果用 Pointer Events 统一处理，触屏拖拽光效在真机上几乎不生效（只有按下那一瞬间闪一下）。**结论是触屏必须监听 `touch` 事件，桌面才用 `pointer` 事件。**

这个坑还有个隐蔽之处：用 `new PointerEvent('pointerdown', {pointerType:'touch'})` 手工派发是测不出来的 —— 手工事件不会触发浏览器的滚动手势识别，`pointermove` 会照常触发。必须用 CDP 的真实触摸序列（`Input.dispatchTouchEvent`）才能复现。`tools/verify-drag.js` 就是这么测的。

### 三个实现约束

- **拖尾点用对象池**（预建 20 个 DOM 循环复用），移动时零创建/销毁
- **淡出用 Web Animations API**，不切 class、不读 `offsetWidth`，所以没有强制回流（切 class 重启动画每次都会触发布局）
- **绝不给池里的点写 `will-change`**：20 个点等于 20 个图层常驻显存，会让常驻合成层从 6 涨到 27。`verify-perf.js` 会直接报错拦住这种写法

### 全部会自动关闭的情况

- 系统开启「减少动态效果」→ 追光、光斑、涟漪、**拖拽光效**、翻页吸附全部停用
- 触屏设备 → 不渲染追光（没有指针），但保留拖拽光与涟漪
- `ui.lightEffects: false` → 整层关闭

## 三之四、首页的「活着的」细节

参考了 `cjchn/home-page`（即 `無名の主页` 的分支）的思路，挑了四样适合这里、且不破坏极简气质的东西。**只借鉴想法，没有拿它的代码**——那个项目作者自己写着「代码相当杂乱且质量低下」并已停止维护，而且它是 Vue + Vite + 依赖一堆第三方 API 的构建型项目，和这里零依赖纯静态的定位完全不同。

| 功能 | 表现 | 开关 |
| --- | --- | --- |
| **载入动画** | 首屏一条细线走完就退场，约 0.9 秒 | `live.loading` |
| **实时时钟** | `15:32 · 周六 11 月 9 日`，等宽数字，跳动不抖 | `live.clock` |
| **时光进度条** | 「今年已过 86%」+ 一条 2px 发丝线 | `live.progress` |
| **一言** | 一句话，点一下换一句 | `live.quote` |
| **音乐浮窗** | 默认关闭；填音源出播放按钮，只填链接变成入口 | `music.enabled` |

### 载入动画的三条约束

1. **每次会话只出现一次**（`sessionStorage` 记标记），来回翻页不会再挡。
2. **硬上限 0.9 秒**，不管资源加载到哪一步，到点就退场——不能为了动画让人等。
3. **系统开了「减少动态效果」就完全不出现**；没有 JS 时有 `<noscript>` 兜底样式，不会卡在空白遮罩上。

### 一言为什么默认用本地列表

公开的一言接口随机返回，风格跨度极大。我实测拉到的一句是「每一次匆忙的路过，都是一次永久的离别」——这种放在社交场合给人看的主页上会很尴尬。

所以默认用 `config.js` 里的 `quotes` 本地列表：**内容可控、零网络、零失败**。点一下换一句。想联网就把 `live.quoteRemote` 改成 `true`（接口我测过，`Access-Control-Allow-Origin: *`，跨域没问题，5 秒超时后自动回落到本地列表）。

### 音乐浮窗：绝不自动播放

两种形态，取决于你填了什么：

- **填了 `music.src`**（mp3 直链）→ 出现播放按钮，点击才播，`preload="none"` 不抢带宽
- **只填 `music.link`** → 变成一个「去听歌」的跳转入口，指向你的网易云

浏览器普遍拦截自动播放，而且主页常在给别人看，突然出声很失礼。所以默认 `enabled: false`，要用才打开。

### 我故意没做天气

`無名の主页` 有实时天气，需要「高德开放平台」的 Key。这台是纯静态站点，Key 只能写在前端代码里，**等于公开**（拿到就能刷你的配额）。免费第三方天气接口又经常挂。为了一个社交场合基本用不上的信息去牺牲安全性，不划算。

真需要的话，正确做法是加一个自己的服务端转发 Key——那就不叫纯静态站了，成本远大于收益。

## 三之五、字体：MiSans

全站字体是 **MiSans**（小米，免费商用）。

### 为什么分两个文件

| 文件 | 管什么 |
| --- | --- |
| `assets/css/fonts.css` | `@font-face` 声明，300 条（3 个字重 × 100 个 unicode 分片） |
| `assets/css/typography.css` | 字重阶梯：谁能用 700、谁只能 600、谁必须 400 |

`fonts.css` 是从 [misans](https://github.com/dsrkafuu/misans)（Apache-2.0）的
分片 CSS 生成的，**改了字重的标定**：那个包里每个字重写着 MiSans 的原生重量
（Regular 330 / Semibold 520 / Bold 630），而 CSS 里写 `font-weight:600` 时
浏览器按"就近取大"会挑 630、写 500 会挑 520 —— 整套映射全乱。这里统一改成
**400 / 600 / 700**，一个数字一层。

woff2 **就在仓库里**（`assets/fonts/`，300 个分片 / 5.8MB），不走外部 CDN ——
静态站本来就该把这些收进来，CDN 一抖，换字体的效果就直接变回系统字体。
仍然是按 `unicode-range` 分片：浏览器只下载页面真正用到的那十几片
（实测首屏 34 片、约 300KB），新加的字（比如下周换歌单里的生僻字）会自动取片。
分片声明的代价是 CSS 本身有 88KB（gzip），这是"换字体"这件事的固定成本。

想更新字体（换版本 / 加字重）：改 `tools/fetch-fonts.py` 里的 `PLAN`，
然后 `python tools/fetch-fonts.py` —— 它会重新下载分片并重写 `fonts.css`。
**别手工改 fonts.css**，那个文件是生成物。

### 字重只有三档

```
700  标题 / 首屏名字 / 主数字        —— 一眼定层级
600  卡片标题 / 按钮 / 导航 / 小标签 —— 交互与"能点的东西"
400  正文 / 说明 / 副标题            —— 只负责读
```

规则写在 `typography.css` 里，一处能看全。原来散在 8 个文件里的 500 会落到
600（MiSans 在 400/600 之间的灰度差比 Inter 小，500 会糊成一片）。

`--font-mono` 也指向 MiSans：项目里它承担的其实是"数字 + 小标签"，不是源码。
MiSans 的数字有 `tnum` 特性，`typography.css` 给这些位置统一开了
`font-variant-numeric: tabular-nums`，竖排列表里 01…10 照样对齐。
唯一的例外是「终端」主题：那里的等宽就是它的性格，保留真等宽。

### 主题里的字体写在 JS 里

⚠️ `themes.js` 会把 7 套风格的 `--font-sans / --font-display / --font-mono`
**内联**写到 `<html>` 上，内联优先级高于样式表。所以换字体要改 `themes.js`
（7 × 3 条），只改 `tokens.css` 是不生效的 —— `tokens.css` 里那份只是
JS 没加载时的兜底。

## 四、头像

`config.js` 的 `site.avatar` 支持三种状态：

| 值 | 效果 |
| --- | --- |
| `""`（默认） | 用字母方块（`site.initials`），页头、页脚显示 |
| 图片网址 | 页头 / 页脚 圆形（34 / 26px）、首页顶部 64–84px 圆形 |
| 内嵌图片（data URL） | 同上，图片直接存进 `config.js`，不依赖外部图床 |

**推荐用编辑器上传**（基础 → 头像 → 选择图片）：会自动居中裁成正方形、缩到 256×256、压成 WebP（不支持则 JPEG），通常只有 20–40 KB。也支持直接填网址。

> 只有配置了图片，首页顶部才会出现头像；否则保持原来的极简版式，避免和页头的字母块重复。

### 深色主题下"头像有白边"的真正原因

这个 bug 修过两轮都没根治，因为前两次都在改 `<img>` 自己（去掉 border、
换成 `border-radius: 50%`）。真正的病灶在**外面那层壳**：

```html
<span class="brand__mark" id="brandMark">
  <img class="brand__avatar" src="...">
</span>
```

`#brandMark` / `#footerMark` 本身就是 `.brand__mark` —— 字母方块的容器，
样式是 `border-radius: 10px` + `background: var(--text)`。
深色主题下 `--text` 接近纯白，于是**圆头像后面永远垫着一个白色圆角方块**，
四个角从圆边露出来。img 再怎么设圆角都盖不住它。

修法：`render.js` 在有图片时给外壳加 `.is-photo`，CSS 里把它变成
圆形 + 透明底 + `overflow: hidden`，由外壳负责裁切；img 铺满 100%
再 `scale(1.08)`，顺带把原图边缘的浅色过渡也裁掉。

`verify.js` 里有 5 条断言钉住这件事（外壳加类 / 撤类 / 圆形 / 透明 / 裁切），
避免以后又只改 img。

## 五、内容编辑器（admin.html）

访问 `https://你的域名/admin.html`（或本地打开 `admin.html`）。

- **账户与口令**：首次交付时随项目一起给你，记在仓库外的 `管理凭据.txt`（本地文件，不会上传到 GitHub）。源码里只有盐和哈希，没有明文。
- 登录后可改：站点信息、合作状态、首页按钮、四个模块的标题与开关顺序、关于我（段落 / 信息表 / 标签）、业务卡片、喜好卡片、社交链接、主题色与动效开关。
- 卡片类内容支持**添加 / 删除 / 上下移动**。
- 改动先存在本机浏览器（草稿），点「发布」时生成新的 `config.js`，然后二选一：**不用令牌**（复制→GitHub 编辑页粘贴→Commit，最安全）或**令牌一键推送**（先点「先检查连接」，全部 ✓ 才能提交）。详见下一节。

### 凭据是怎么存的

源码里**没有口令明文**，只存 `salt + SHA-256` 的摘要（`assets/js/admin.js` 顶部）。校验在本机完成。

需要说清楚的是它的边界：这是**入口锁**，挡的是顺手点开乱改，不是密码学意义上的安全防护——有能力读源码的人可以绕过它。真正决定谁能改线上内容的，是你的 **GitHub 账号**：没有仓库写权限，改什么都传不上去。所以这层锁的定位是「防误碰 + 防好奇」，不是「防攻击」。

### 改账户或口令

1. 进编辑器 → 发布抽屉 → 底部「更改管理账户 / 口令」→ 填新账户与口令 → 生成。
2. 把生成的三行替换到 `assets/js/admin.js` 顶部的 `ADMIN` 区块。
3. commit 一次，所有设备同步生效（只在编辑器里填、不提交则仅本机有效，因为本地覆盖存在浏览器里）。

> 新建 GitHub 令牌时，建议用 *Fine-grained token*，只授权这一个仓库的 **Contents: Read and write**，用完可随时撤销。令牌只存在本机浏览器，不会随代码上传。
>
> 万一凭据文件丢了：直接生成一套新的替换掉即可，旧口令立即失效，不需要「找回」。

## 六、发布内容：两条路，以及「提交失败」怎么办

改完内容点「发布」，抽屉里有两条路线。

### 路线一：不用令牌（推荐）

```
复制 config.js  →  打开 GitHub 编辑页  →  全选粘贴  →  点 Commit
```

**为什么推荐它**：浏览器里不存任何令牌，**就没有令牌可泄露**。你本来就是登录状态，
2FA 由 GitHub 自己弹、自己验，站点完全不接触任何凭据。对「既要简单又要安全」这个要求，
这条路是答案——它比任何令牌方案都安全，因为攻击面为零。

手机上也能做（复制后切到 GitHub App 或浏览器粘贴）。

### 路线二：用令牌一键推送

填一个 GitHub Token → 点**「先检查连接」**→ 全部 ✓ 之后提交按钮才可点。

提交前会做 5 项检查，任何一项失败都会直接告诉你原因和修法：

| 检查 | 失败时的含义 |
| --- | --- |
| 令牌格式 | 不是 `ghp_` / `github_pat_` 开头，或带了空格换行 |
| 令牌有效 | 401：已过期或被撤销 |
| 权限范围 | 经典 `ghp_` 令牌必须勾 **repo** |
| 仓库可访问 | 见下方「404 陷阱」 |
| 能读到配置文件 | 分支名或路径不对 |

### 为什么以前会「提交失效」

**你可能踩的是这个坑：GitHub 对「没权限」和「不存在」都返回 404。**

这是 GitHub 的刻意设计（避免泄露仓库是否存在），但它让错误极难自查——
令牌明明没授权到仓库，返回的却是「Not Found」，看起来像文件没了。

旧版代码把 404 当成「文件不存在」，于是跳过读 sha、直接去写，写入又 404，
最后只显示一句「提交失败（404）」。**这是旧版的缺陷，已修**：现在 404 会被
翻译成「令牌没授权到这个仓库，去 Fine-grained 设置里把 Repository access 选成
Only select repositories → 本仓库，Permissions → Contents 设为 Read and write」。

其他状态码也都给了具体含义：401 令牌失效、403 权限或限流、409 内容冲突需刷新、
422 编码或体积异常、429 请求过频。

### 创建令牌的正确步骤（Fine-grained）

1. 打开 <https://github.com/settings/personal-access-tokens/new>
2. **Token name**：随便写，比如 `zotrod-homepage`
3. **Expiration**：建议 90 天（到期重发，比永久的更安全）
4. **Repository access** → 选 **Only select repositories** → 只勾 `ZoTtfoy.github.io`
5. **Permissions** → **Contents** → 设为 **Read and write**（其余都不用给）
6. 生成后立刻复制（页面关掉就再也看不到）

> 为什么不用「用 GitHub 账号登录」那类方式？我实测过：GitHub 的 Device Flow 端点
> （`github.com/login/device/code`）**不返回任何 CORS 头**，浏览器发不出去，
> 所以纯静态站点根本调不通。而 OAuth App 的授权范围是 `repo`——等于**你所有仓库的读写权**，
> 比上面这个「只授权一个仓库的 Contents」宽得多。真要论安全性，Fine-grained token 反而更好。

## 七、编辑器自检

```bash
node tools/verify-admin.js    # 凭据哈希 / 序列化无损
```

## 十之一、手机多比例适配

手机屏幕比例跨度极大：16:9 的老机型、19.5:9 的新机、20:9 的长条，还有折叠屏外屏和横屏。

第一版的做法是「按可用高度分四档，整站共用一个档位，装不下就压字号」。它确实做到了 15 种机型全部一屏装下 —— 但代价是手机上出现了这样的数字：

| 元素 | 压到最紧时的字号 |
| --- | --- |
| 计算器选项 | 9.9px |
| 报价行 | 9.6px |
| 摘要卡副标题 | 9.9px |
| 游戏 UID | 9.3px |

而同一批机型的**内容填充率只有 26%~62%**：屏幕上大半是空白，字却小到看不清。用空白换字号，是本末倒置。

### 现在的分工：字号看宽度，留白看高度

| 决定因素 | 归属 | 规则 |
| --- | --- | --- |
| 字号 | `blocks.css` / `gaming.css` 的宽度媒体查询 | 只跟屏幕**多宽**有关，与这一屏装不装得下无关 |
| 留白 | `fit.css` 的高度档位 | 只调内边距、外边距、间隙、图标尺寸，档位规则里**一条 `font-size` 都没有**（横屏那套小一号字阶是「方向」特例，单独成段） |

档位仍然按「从最宽松开始试，装不下就降一档」的方式试探，但属性从 `<html data-fit>` 挪到了**每一屏自己身上**（`.hero` / `.section`）：

| 档位 | 做法 |
| --- | --- |
| `roomy` | 设计稿留白 |
| `tight` | 收紧页头与卡片内边距 |
| `snug` | 进一步压缩；隐藏重复信息（Q4 摘要卡的平台名） |
| `micro` | 只压间距，不删内容、不缩字 |

**为什么必须按屏分档**：内容高度是「就高不就低」的。Q4（计算器 + 报价表）始终是最高的那一屏，它一装不下，Q1/Q5 这些只填了 40% 的屏也跟着降档。实测 390×844 的 Q1 内容只占 55%，却因为 Q4 超屏被判成 `snug`。改成按屏分档后，每屏拿到自己能承受的最宽松档位：

```
390×844  top:roomy listen:roomy gaming:roomy repair:roomy links:roomy contact:roomy
375×667  top:roomy listen:roomy gaming:roomy repair:micro links:roomy contact:roomy
320×568  top:snug  listen:tight gaming:snug  repair:micro links:roomy contact:tight
```

### 可读性下限（硬线，任何档位都不许破）

| 类别 | 下限 |
| --- | --- |
| 正文（曲名 / 游戏名 / 平台名 / 账号 / 计算器选项 / 简介） | 13.5px |
| 密集表格（报价项 / 价格） | 12.5px |
| 辅助信息（标签 / 副标题 / 脚注） | 11px |
| 可点区域高度 | 34~38px |

`verify-devices.js` 直接量 `getComputedStyle().fontSize` 来守这条线 —— 它比「每章高度 = 屏高」更接近用户真正在意的东西。

### 腾空间靠改结构，不靠缩字

| 改动 | 省下 | 说明 |
| --- | --- | --- |
| 报价表折叠成 `<details>` | ~150px | 手机上默认收起（`repair.js` 摘掉 `open`），摘要行显示「10 项 · 2 类」，点开才展开；桌面默认展开 |
| 联系卡改两行 | 0（反而变高） | 原来「图标 + 账号」横排，390px 下账号只剩 100px，微信号/QQ 号必被省略号截断；改成两行后账号独占整行 |
| Q4 摘要卡去掉平台名 | 20px | 图标 + 「闲鱼」+ 标题说的是同一件事 |
| 计算器右上角提示 | 33px | 「选完即出价」是自证信息，且 360px 下会把标题行挤成两行 |

### 实测结果

15 种机型（375×667 到 430×932、344×882 折叠屏、320×568、844×390 横屏）：

- 正文 13.8~15.2px、辅助 11.5~12.2px（竖屏全机型一致）
- 内容填充率 39%~82%，不再是「一半空白 + 9px 字」
- 内容底部余量 ≥ 8px（给底部页码条留位）
- 除两处文档化的例外，每章高度仍等于屏高，强制吸附不降级

### 两处文档化的例外

1. **320×568 的 Q4**：压到 `micro` 仍差约 40px。不缩字号，改为标 `data-tall`、吸附降级为 proximity，允许把那屏滚完。
2. **844×390 横屏**：页头就占 72px，390 的高度放不下竖版页面。横屏改用一套独立的小一号字阶（正文 12.5px 起，内容一条不删），仍超屏时整站降级为可滚动。

两者都在 `verify-devices.js` 的 `ALLOW_TALL` 白名单里显式列出 —— 例外要写在代码里，而不是让断言悄悄放过。

## 十之二、性能

性能问题不会报错，只会"感觉有点卡"。所以做了两件事：**先测量，再优化**，并把指标固化成了回归测试。

### 优化前后

| 指标 | 第一轮前 | 第一轮后 | 本轮后 |
| --- | --- | --- | --- |
| 滚动帧耗时（中位） | 109.1ms（≈9 FPS） | 19.3ms | **16.7ms（60fps 满帧）** |
| p95 帧耗时 | — | 33.4ms | **16.7ms** |
| 掉帧率 | — | 6.3% | **0.6~1.1%** |
| 滚动期间布局读取 | 181 次 | 1 次 | 1 次 |
| 常驻合成层 | 61 个 | 6 个 | 6 个 |
| 单次主题切换 | 106ms | 51ms | **40ms** |

> 60fps 的理论帧间隔是 16.67ms。中位与 p95 都是 16.7ms，说明**基本不掉帧**——
> 只有极少数帧（p99）会出现一次 33.4ms。这已经是软件渲染环境下的上限。

### 关于 120fps

这个要如实说明：**能不能跑 120fps，取决于设备屏幕，不取决于页面。**

- 页面这边能做的，是把每帧成本压到远低于 8.3ms（120Hz 的预算）。现在滚动期间主线程几乎不做事——布局读取 1 次、长任务 0 个、脚本耗时占比极低，合成层只剩 6 个，所以**在 120Hz 屏幕上会自然跑满 120fps**。
- 实测在 60Hz 环境下的帧分布：p50 / p90 / p95 全部 16.7ms，掉帧率 0.6~1.1%。这已经是软件渲染环境的天花板——**继续优化也没有意义了，因为瓶颈已经不在页面**。
- 但我无法在这个环境里"看到"120fps：无头浏览器固定 60Hz 节拍，测出来的上限就是 16.7ms。所以我没有伪造一个 120fps 的数字给你。

你也可以在当前页面按 F12 → Rendering → Frame Rendering Stats，或在支持高刷的显示器上直接感受。

### 六个真实的问题

**1. 光晕的 `filter: blur(90px)` 是最大元凶**

我给 900px 的光晕加了 90px 高斯模糊，又让它做缩放动画。缩放会让浏览器**每帧重新栅格化那次大面积模糊**，滚动直接掉到 9 FPS。

修法：把模糊"画"进渐变里（用多段 `radial-gradient` 模拟景深），只用 transform 做动画。同时把尺寸从 1080px 收到 640px —— 实测**尺寸比动画方式重要得多**（1080→640 省 8ms，换动画类型只省 1~2ms）。

**2. 61 个元素常驻 `will-change`**

`will-change` 会让浏览器为每个元素预留合成层。我给所有 `[data-reveal]` 和每个 `.container` 都写了它，等于把几十个整屏大小的图层塞进显存。

实际上浏览器在动画期间会自动提升图层，不需要常驻声明。删掉后 61 → 6。

**3. 两套 scrollspy 各读一遍布局**

`motion.js` 和 `paged.js` 各自算「当前在哪一页」，每帧对 6 个区块各调一次 `getBoundingClientRect`，滚动一次 181 次强制布局。

修法：`paged.js` 算一次，通过 `site:pagechange` 事件广播；`motion.js` 在翻页模式下直接复用，不再自己遍历。配合位置缓存 + `ResizeObserver`，**181 次降到 1 次**。

**4. 光晕只要"在变"，滚动就掉帧（本轮的新发现）**

上一轮把光晕缩到 520px 后以为够了，但用 4 轮采样测下来仍有 3~5 次掉帧。逐项排查发现：

| 配置 | 掉帧（3 秒约 110 帧） |
| --- | --- |
| 520px + 位移漂移 + 透明度呼吸 | 5 |
| 380px + 两段渐变 | 3 |
| 380px + 只保留透明度动画 | 4 |
| 380px + **滚动时完全静止** | **0** |

反直觉的是：掉帧与"变什么"无关，与"变不变"有关。光晕是覆盖大半屏的半透明层，任何变化都要合成器重新混合它覆盖的像素。

所以最终策略是**静止时呼吸、滚动时完全静止**。视觉上没有任何损失——你盯着看的时候它一直在动；滚动时注意力在内容上，谁也注意不到背景停了一瞬。

顺带把触发时机前置到了 `wheel` / `touchmove`（早于 `scroll` 事件），让背景在滚动开始的那一帧之前就停住。

**5. 噪点层和追光：只要"存在"就掉帧（本轮的新发现）**

噪点原来用 SVG `feTurbulence` 分形噪声，浏览器每次重绘都要重新计算噪声图——这是光晕之后的第二大掉帧源。改成预渲染的点阵纹理后仍有 8/170 掉帧，查下去才明白：**它是覆盖全屏的半透明层，只要存在，合成器每帧都要为它多做一遍混合，与纹理内容无关。**

同样的道理适用于追光：一个 460px 的半透明渐变层，每帧移动它都要重新混合覆盖区域。

于是三者用同一套策略——**滚动时全部静止**：

| 元素 | 静止时 | 滚动时 |
| --- | --- | --- |
| 光晕 | 透明度呼吸 | 动画暂停 |
| 噪点 | 显示颗粒 | 整层隐藏 |
| 追光 | 跟随指针 | 停止跟随，停手 180ms 后补上 |
| 顶栏 | 毛玻璃模糊 | 实色背景 |

视觉上察觉不到，因为滚动时注意力都在内容上。掉帧率从 6.3% 降到 1% 以内。

另外把卡片光斑的 `getBoundingClientRect` 也做了缓存（`WeakMap` + 滚动/缩放才失效），指针在卡片内移动时不再触发布局读取。

**6. 主题切换给全站 740 个元素加过渡**

`.theme-switching *` 让每个元素都声明 `transition`，一次切换要强制重算整个文档的样式。

修法：只给真正有大面积色块变化的元素加过渡（卡片、按钮、面板等约 20 类）。文字颜色本来就靠继承，不必逐个声明。

### 另外两处小优化

- **顶栏毛玻璃滚动时临时关闭**：`sticky + backdrop-filter` 每帧都要重新模糊顶栏覆盖区域，占 5.5ms。滚动期间切换成实色背景，停手 160ms 后恢复，肉眼察觉不到。
- **微粒动画改用 `transform`**：原来动画 `background-position`，每帧重绘一整屏；改成平移一层纹理走合成层。

### 复核

```bash
node tools/verify-perf.js
```

16 项断言，会把上面这些指标重新量一遍，任何一项回退都会失败。阈值留了余量（无头环境是软件渲染，真机有 GPU 更快）。

> 一个说明：**微粒（stars）仍是可选项里最耗的**，开启后滚动约 24ms（≈42 FPS）。它默认关闭，需要氛围感时再开。我没有为了它牺牲默认体验。

## 十二、常见问题

**改了 config.js 但页面没变？**
先强制刷新（Ctrl/Cmd + Shift + R）。线上请确认 `git push` 成功、Actions 显示绿色对勾，再等 1–2 分钟。

**Actions 失败 / 页面 404？**
检查 Settings → Pages 的 Source 是否为 **GitHub Actions**（不是 "Deploy from a branch"），以及仓库是否为 Public（或账号具备 Pages 权限）。

**本地双击打开和线上不一样？**
`file://` 下浏览器对部分 API 有限制（例如剪贴板）。用 `python -m http.server 8000` 起本地服务即可完全一致。

**想恢复「跟随系统主题」？**
在浏览器控制台执行 `localStorage.removeItem('zotrod-theme')` 后刷新。
